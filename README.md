# create_disk

Ansible-роль: выбрать один новый диск без разделов, создать GPT, отдельные
VG/LV, файловую систему XFS и смонтировать её в `mount_point` с записью в fstab.

## Установка и запуск

На управляющей машине нужны Ansible и коллекции:

```sh
python3 -m pip install 'ansible==12.1.0'
ansible-galaxy collection install -r requirements.yml
```

Репозиторий разместите как `roles/create_disk` либо добавьте его родительский
каталог в `ANSIBLE_ROLES_PATH`. Пример playbook:

```yaml
- hosts: storage_servers
  become: true
  roles:
    - role: create_disk
      mount_point: /data
```

Целевая система — Linux семейства Debian или Red Hat с Python, root/sudo,
работающим udev и современными util-linux/LVM: нужны `lsblk --json` с полем
`MOUNTPOINTS`, `wipefs --json` и JSON-отчёты `vgs`, `lvs`, `pvs`.
Роль устанавливает lvm2, parted, xfsprogs, util-linux и udev/systemd-udev.
Не запускайте роль на контейнере или хосте с дисками, которые нельзя изменять.

## Переменные

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `mount_point` | `/data` | Новый абсолютный путь; каталог ещё не должен существовать |
| `create_disk_vg_base` | `vg_data` | Базовое имя группы |
| `create_disk_lv_base` | `lv_data` | Базовое имя логического тома |
| `create_disk_device` | `""` | Необязательный точный путь, например `/dev/sdb` |
| `create_disk_wipe_signatures` | `false` | Явное разрешение очистить старые сигнатуры на выбранном диске и новом разделе |

При первом запуске выбираются `vg_data` и `lv_data`. Если имя VG **или** имя LV
уже занято, выбирается первая свободная пара с одинаковым суффиксом:
`vg_data-1`/`lv_data-1`, затем `vg_data-2`/`lv_data-2` и т. д.
Имена LV проверяются во всех группах, хотя LVM технически допускает одинаковые
имена LV в разных VG. Пропуски в нумерации переиспользуются.

После добавления второго диска запустите роль с **другим** `mount_point`:

```yaml
- hosts: storage_servers
  become: true
  roles:
    - role: create_disk
      mount_point: /archive
      # Необязательно, но рекомендуется при нескольких новых дисках:
      create_disk_device: /dev/sdc
```

Существующие группы не расширяются, их PV не удаляются. На каждый обработанный
диск создаётся отдельная VG с одним LV. После успешного запуска доступен факт
`create_disk_result` с полями `device`, `partition`, `vg`, `lv`, `mount_point`.

## Защита данных и ограничения

- Автоматически выбирается ровно один диск `sd*`, `vd*`, `xvd*` или `nvme*n*`.
  При отсутствии кандидатов или нескольких кандидатах роль завершается ошибкой.
  `create_disk_device` сужает выбор, но не отключает проверки безопасности.
- Отбрасываются разделённые, смонтированные, read-only, removable-устройства,
  диски с дочерними устройствами/holders и существующие PV, в том числе PV без VG.
- Отсутствие разделов не доказывает отсутствие данных. Перед разметкой
  проверяется `wipefs --no-act`; по умолчанию обнаруженные сигнатуры запрещены.
  Сырые данные без распознаваемых сигнатур определить нельзя: оператор должен
  убедиться, что диск действительно предназначен для этой операции.
- На oVirt/RHV могут встречаться остаточные сигнатуры старых дисков.
  `create_disk_wipe_signatures: true` разрешает их удаление **только после ручной
  проверки назначения диска**. Проверки занятости и существующих PV сохраняются.
  `wipefs` удаляет сигнатуры, а не затирает всё содержимое диска.
- После создания раздела проверяются его монтирование и внутренние сигнатуры:
  старый PV label на смещении 1 MiB может быть невидим на уровне целого диска.
  Если обнаружены сигнатуры без разрешения на очистку, роль остановится; GPT
  к этому моменту уже создана. Ожидание udev ограничено 30 секундами.
- Существующий `mount_point`, включая пустой каталог или symlink, вызывает
  отказ **до установки пакетов и операций с диском**. Это намеренно одноразовая
  роль provisioning, а не идемпотентное сопровождение существующих томов.
  Повтор с той же папкой завершится ошибкой, а не создаст новый том.
- После частичного сбоя автоматическое продолжение не предусмотрено: диск с
  уже созданным разделом перестаёт быть кандидатом. Сначала вручную проверьте
  состояние. Не очищайте его автоматически ради повторного запуска.
- Запуски на одном сервере должны быть последовательными. Повторная проверка
  имени VG уменьшает риск гонки, но не заменяет блокировку от внешних LVM
  операций. Не выполняйте параллельно другие операции provisioning/automount.
- `--check` не моделирует разметку и отклоняется до изменений. Ошибки чтения
  состояния LVM и неожиданные ошибки `findmnt` не игнорируются.

## Проверки

Из корня репозитория с `ansible-playbook` в PATH:

```sh
python3 tests/run.py
```

Проверки запускают реальные Ansible-задачи выбора имён/устройств на синтетических
отчётах и проверяют отказ полной роли для существующего каталога. Проверяются
20 сценариев: свободные/занятые имена, суффиксы и пропуски, сброс фактов между
вызовами, SATA/NVMe, неоднозначный и явный выбор, mounted/read-only/removable,
разделы, holders и PV. Ошибки ожидаемых отказов перехватываются и проверяются.
Все сценарии должны закончиться `failed=0`, `changed=0`.

Эти проверки **не подтверждают** фактическое создание GPT/LVM/XFS и монтирование.
Для интеграционного теста нужна одноразовая VM с отдельным пустым диском:

1. Запустить роль с `/data`; проверить `pvs`, `vgs`, `lvs`, `findmnt /data`
   и запись в `/etc/fstab`.
2. Добавить второй пустой диск и запустить с `/archive`; проверить отдельную
   `vg_data-1/lv_data-1` и сохранность первого тома/его данных.
3. Повторить запуск с существующим каталогом; ожидать отказ без изменений.
4. Проверить сохранение обоих монтирований после перезагрузки VM.

В текущей облачной среде такой VM нет; интеграционный сценарий не запускался.
