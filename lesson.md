# Урок: как устроена роль create_disk и как проектировать Ansible-роли

Этот урок разбирает текущую реализацию роли из этого репозитория. Читай его
вместе с [tasks/main.yml](tasks/main.yml): это маршрут выполнения. Остальные
файлы раскрывают отдельные этапы этого маршрута.

После урока ты должен уметь разделять playbook и роль, читать условия и
фильтры Jinja, получать состояние сервера, принимать решение по этому состоянию
и только после проверок выполнять изменения.

## 1. Почему роль стала длиннее

Исходная задача выглядит коротко: найти диск, создать LVM и смонтировать.
Но перед изменением диска нужно ответить на вопросы, которые раньше были
неявными предположениями:

- Действительно ли диск свободен, если на нём нет разделов?
- Не является ли он PV существующей группы?
- Нет ли на нём файловой системы без таблицы разделов?
- Что делать, если найдено два подходящих диска?
- Какие имена VG и LV свободны?
- Можно ли создавать каталог по переданному пути?
- Когда ядро увидит новый раздел после изменения GPT?
- Что делать, если состояние LVM изменилось во время работы?

Теперь эти вопросы выражены отдельными задачами. Дополнительные строки — это
в основном сбор сведений, выбор и объяснимые отказы. Сама последовательность
создания GPT → PV → VG → LV → XFS осталась небольшой.

Длиннее не всегда означает лучше. Здесь оправдано явно показать проверки,
потому что ошибка выбора диска может уничтожить данные. При этом у роли есть
ограничения: она не умеет автоматически продолжать частично завершённую
разметку и не блокирует сторонние операции с дисками.

Полезная схема проектирования:

```text
Проверить входные параметры
          ↓
Получить текущее состояние сервера
          ↓
Выбрать объект и проверить ограничения
          ↓
Выполнить изменения в порядке зависимостей
          ↓
Сообщить результат и проверить нужное поведение
```

Последний пункт нельзя считать автоматически выполненным после успешного
разбора YAML. В этой роли модули выполняют создание и монтирование, но
отдельной итоговой проверки всей цепочки через `findmnt`/`lvs` пока нет.

## 2. Сначала разберём LVM

Для этой роли цепочка устройств выглядит так:

```text
/dev/sdb                       физический или виртуальный диск
└── /dev/sdb1                   раздел внутри GPT
    └── PV                     physical volume: раздел подготовлен для LVM
        └── vg_data            volume group: группа физических томов
            └── lv_data        logical volume: логический том
                └── XFS        файловая система
                    └── /data  каталог, в который она смонтирована
```

VG в LVM может объединять несколько PV, а внутри VG можно создавать несколько
LV. Однако наша роль намеренно использует более простую модель: один новый
диск → одна новая VG → один LV на всё свободное место.

При добавлении второго диска получаем отдельную цепочку:

```text
/dev/sdc → /dev/sdc1 → PV → vg_data-1 → lv_data-1 → XFS → /archive
```

Первую группу не нужно расширять или пересоздавать. Именно поэтому важно
выбирать новое имя VG, а не просто повторять `vg: vg_data`.

## 3. Inventory, playbook, роль, задача и модуль

**Inventory** описывает, какие серверы доступны Ansible и как к ним подключаться.
**Playbook** содержит список plays. Каждый play задаёт группу серверов,
параметры выполнения и задачи или роли. **Роль** — переиспользуемый набор
задач, переменных и, при необходимости, других ресурсов.

Пример структуры проекта, использующего нашу роль:

```text
project/
├── inventory.ini
├── storage.yml
└── roles/
    └── create_disk/             этот репозиторий
        ├── defaults/main.yml
        ├── tasks/main.yml
        ├── tasks/select_names.yml
        ├── tasks/select_device.yml
        ├── tasks/provision.yml
        ├── requirements.yml
        ├── tests/run.py
        └── lesson.md
```

Пример inventory для собственной тестовой VM:

```ini
[storage_servers]
test-vm ansible_host=192.0.2.10 ansible_user=admin
```

`192.0.2.10` — адрес для примера; подставь адрес своей VM. Ключи SSH и sudo
настраиваются отдельно, пароли в репозиторий не записывают.

Playbook `storage.yml`:

```yaml
---
- name: Подготовить дополнительный диск
  hosts: storage_servers
  become: true
  roles:
    - role: create_disk
      mount_point: /data
      create_disk_device: /dev/sdb
```

`hosts` выбирает серверы из inventory. `become: true` включает повышение
привилегий на целевых серверах. Сам запуск Ansible на управляющей машине
не обязательно должен выполняться от root.

**Задача** вызывает один модуль. Например:

```yaml
- name: Создать каталог
  ansible.builtin.file:
    path: /data
    state: directory
    mode: '0755'
```

Здесь `ansible.builtin.file` — модуль, а `path`, `state`, `mode` — его параметры.
`name` — понятное человеку описание, которое видно в выводе Ansible.

Полное имя модуля называют FQCN: `namespace.collection.module`.
`ansible.builtin` входит в ansible-core, а `community.general` и
`ansible.posix` устанавливаются как коллекции. Версии нужных коллекций
зафиксированы в [requirements.yml](requirements.yml).

Ansible автоматически ищет входные файлы `defaults/main.yml` и `tasks/main.yml`.
Файлы с похожими именами в корне сами по себе ролью не становятся.
`requirements.yml` также не устанавливается автоматически при вызове роли:
для этого отдельно выполняют `ansible-galaxy collection install -r requirements.yml`.

## 4. Зачем несколько файлов tasks

| Файл | Ответственность |
| --- | --- |
| [defaults/main.yml](defaults/main.yml) | Входные переменные и их значения по умолчанию |
| [tasks/main.yml](tasks/main.yml) | Общая последовательность и проверки до разметки |
| [tasks/select_names.yml](tasks/select_names.yml) | Выбор свободной пары имён VG/LV |
| [tasks/select_device.yml](tasks/select_device.yml) | Выбор одного допустимого диска |
| [tasks/provision.yml](tasks/provision.yml) | Разметка, создание LVM/XFS и монтирование |
| [tests/run.py](tests/run.py) | Проверки логики выбора на подготовленных данных |

В `tasks/main.yml` используется:

```yaml
- name: Select an unused VG and LV name
  ansible.builtin.include_tasks: select_names.yml
```

`include_tasks` подключает список задач во время выполнения. После него
выполнение продолжается со следующей задачи основного файла. Отдельного
процесса или изоляции переменных при этом не возникает.

`import_tasks` раскрывает список задач статически при обработке playbook.
Это влияет, например, на отображение задач, применение условий и тегов.
Динамическое подключение удобно для этапов, которые зависят от уже полученных
данных. Однако и статическое подключение здесь в ряде мест было бы допустимо;
делить роль на файлы можно независимо от выбора include/import.

Практический принцип: основной файл должен позволять понять порядок действий
без чтения каждой длинной формулы выбора.

## 5. Defaults — внешний интерфейс роли

```yaml
mount_point: /data
create_disk_vg_base: vg_data
create_disk_lv_base: lv_data
create_disk_device: ''
create_disk_wipe_signatures: false
```

Defaults имеют низкий приоритет и предназначены для переопределения.
Например, значение `mount_point: /archive` в вызове роли заменит `/data`.
Переменные можно задавать также через inventory, `group_vars`, `host_vars`
и `--extra-vars`; у этих источников разные приоритеты. В частности, `-e`
переопределяет обычные переменные роли.

Префикс `create_disk_` уменьшает вероятность столкновения с переменными других
ролей. `mount_point` оставлен без префикса ради существующего интерфейса.
В новой роли разумно сразу использовать префиксы для всех её параметров.

Обрати внимание на типы:

```yaml
create_disk_wipe_signatures: false    # логическое значение
create_disk_device: ''                # строка
```

Строка `'false'` и boolean `false` — разные значения. Поэтому роль проверяет
`create_disk_wipe_signatures is boolean`, а не молча принимает любой ввод.

## 6. Первый этап: проверить параметры и папку

### assert и выражения Jinja

```yaml
ansible.builtin.assert:
  that:
    - mount_point is string
    - mount_point is match('^/[^/].*')
```

`assert` останавливает работу, если хотя бы одно условие ложно.
Список условий означает логическое **И**. В `that` и `when` уже ожидается
выражение Jinja, поэтому оборачивать всё условие в `{{ ... }}` не нужно.

В параметрах модулей, напротив, шаблон записывается явно:

```yaml
path: '{{ mount_point }}'
```

`is string`, `is boolean`, `is match(...)` — тесты: они отвечают на вопрос
о значении. Символ `|` применяет фильтр, который преобразует значение.
Например, `free_disks | length` получает длину списка.

Роль требует абсолютный путь, запрещает компонент `..`, ограничивает набор
символов и длину базовых имён LVM, исключает некоторые зарезервированные
имена LV. Это проверки ожидаемого формата, а не полная нормализация путей
или замена всех проверок, встроенных в LVM.

### stat, register и follow

```yaml
ansible.builtin.stat:
  path: '{{ mount_point }}'
  follow: false
register: create_disk_mount_stat
```

`stat` получает сведения о пути, а `register` сохраняет результат модуля
в переменную. Затем можно обратиться к полю:

```yaml
create_disk_mount_stat.stat.exists
```

`follow: false` означает, что для символической ссылки проверяется сама
ссылка. Роль не должна принять уже существующую ссылку за новый каталог.
Это не гарантирует отсутствия ссылок во всех родительских каталогах пути.

Отказ при существующем каталоге намеренный: эта роль создаёт новое хранилище.
Даже пустая папка сейчас запрещена. Иначе монтирование могло бы скрыть уже
лежащие в ней файлы или повторный запуск начал бы выбирать следующий диск.

Затем роль отклоняет `--check`. Check mode — это попытка спрогнозировать
изменения без их применения, но результат зависит от поддержки каждого
модуля. Без реально созданного раздела нельзя достоверно проверить дальнейшую
цепочку этой роли, поэтому полноценный прогноз здесь не реализован.

## 7. Получение фактов и установка пакетов

`ansible.builtin.setup` собирает факты о целевом сервере:

```yaml
gather_subset: ['!all', min, hardware]
```

Здесь выключается сбор всех наборов по умолчанию и запрашиваются минимальные
системные сведения и аппаратные факты. Они доступны в `ansible_facts`.
Например, `ansible_facts.os_family` нужен для выбора пакета udev:

```yaml
"{{ 'systemd-udev' if ansible_facts.os_family == 'RedHat' else 'udev' }}"
```

Это условное выражение: одно значение при истинном условии, другое — иначе.
Роль заранее проверяет, что семейство — Debian или RedHat, поэтому `else`
здесь не означает обещание поддержки любых других дистрибутивов.

Модуль `package` использует подходящий системный менеджер пакетов.
`state: present` требует наличия пакета; это не требование обновить его
до самой новой версии.

## 8. Чтение состояния: command, argv, loop и register

Роль получает JSON-отчёты от `vgs`, `lvs` и `pvs`:

```yaml
ansible.builtin.command:
  argv: '{{ item }}'
loop:
  - [vgs, --reportformat, json, -o, vg_name]
  - [lvs, --reportformat, json, -o, lv_name]
  - [pvs, --reportformat, json, -o, pv_name]
register: create_disk_lvm_reports
changed_when: false
```

`loop` выполняет задачу для каждого элемента списка. Текущий элемент доступен
как `item`; в этом примере элемент — тоже список аргументов команды.
Короткая запись `[a, b]` в YAML означает тот же список, что и строки с `-`.

`command` запускает программу без shell. `argv` передаёт аргументы раздельно:
не требуется собирать строку с кавычками и рассчитывать на разбор shell.
Операторы `|`, `>`, `&&` при таком запуске не выполняются как операторы shell.
Если нужен специализированный модуль, для изменения состояния обычно лучше
выбрать его; `command` здесь используется для структурированного чтения.

Обычный результат команды содержит `stdout`, `stderr`, `rc`.
При `register` на цикле результаты лежат в списке `results`:

```text
create_disk_lvm_reports.results[0].stdout  → вывод vgs
create_disk_lvm_reports.results[1].stdout  → вывод lvs
create_disk_lvm_reports.results[2].stdout  → вывод pvs
```

Индекс начинается с нуля. `changed_when: false` означает «не считать эту
задачу изменением» в отчёте Ansible. Это **не** механизм запрета записи:
безопасность зависит от самой команды. Здесь команды только читают отчёты.
Ненулевой код возврата по умолчанию остаётся ошибкой.

Если чтение LVM не удалось, продолжать с выдуманным пустым списком нельзя:
«не смогли прочитать группы» и «групп нет» — разные состояния.

## 9. Как разобрать JSON и выбрать имена

Упрощённый ответ `vgs` выглядит так:

```json
{"report": [{"vg": [{"vg_name": "vg_data"}, {"vg_name": "vg_data-1"}]}]}
```

В роли цепочка преобразований такая:

```jinja2
(create_disk_lvm_reports.results[0].stdout | from_json).report[0].vg
| map(attribute='vg_name')
| map('trim')
| list
```

Разберём её по шагам:

1. `stdout` — строка с JSON.
2. `from_json` превращает её в словари и списки.
3. `.report[0].vg` выбирает список записей о группах.
4. `map(attribute='vg_name')` берёт имя из каждой записи.
5. `map('trim')` убирает пробелы по краям каждого имени.
6. `list` материализует результат в обычный список.

Получается `['vg_data', 'vg_data-1']`. Аналогично получаются списки LV и PV.

### set_fact хранит вычисленный результат

```yaml
ansible.builtin.set_fact:
  create_disk_selected_vg: ''
  create_disk_selected_lv: ''
```

`set_fact` задаёт переменную для текущего хоста. Она доступна последующим
задачам и может сохраняться между вызовами роли в том же запуске Ansible.
Это не локальная переменная отдельного файла и не запись на диск сервера.
Без отдельного включения кеширования нельзя рассчитывать на неё в следующем
запуске `ansible-playbook`.

Поэтому выбранные имена и список кандидатов явно сбрасываются при новом
вызове. Иначе можно случайно использовать результат предыдущего выбора.

### Алгоритм свободной пары

Перебираем номера `0, 1, 2, ...`. Для нуля суффикс пустой, далее `-1`, `-2`:

```jinja2
{{ '' if item == 0 else '-' ~ item }}
```

`~` соединяет строки и приводит число к строковому представлению.
Пара принимается, только если одновременно:

- ещё ничего не выбрано;
- кандидат VG отсутствует в списке групп;
- кандидат LV отсутствует в списке логических томов.

| Имеющиеся VG | Имеющиеся LV | Новая пара |
| --- | --- | --- |
| нет | нет | `vg_data` / `lv_data` |
| `vg_data` | `lv_data` | `vg_data-1` / `lv_data-1` |
| `vg_data`, `vg_data-1` | `lv_data`, `lv_data-1` | `vg_data-2` / `lv_data-2` |
| `vg_data`, `vg_data-2` | `lv_data`, `lv_data-2` | `vg_data-1` / `lv_data-1` |
| нет | `lv_data` в другой VG | `vg_data-1` / `lv_data-1` |

Последний вариант — наше правило именования. Сам LVM разрешает одинаковые
имена LV в разных VG. Мы проверяем LV глобально, чтобы обе части новой пары
имели один суффикс и не повторяли уже использованное имя.

В цикле нет `break`: после выбора условие `create_disk_selected_vg == ''`
становится ложным, и остальные итерации пропускаются.

Почему верхняя граница — количество VG плюс количество LV плюс один?
Если всего есть N записей, они могут занять не более N разных номеров
кандидатов. Среди N+1 номеров хотя бы один свободен. `range(0, N+1)`
выдаёт числа от 0 до N, поскольку правая граница не включается.

Это выбор первого свободного номера, а не счётчик «последний номер + 1».
После удаления группы освободившийся номер может использоваться снова.

## 10. Как роль определяет подходящий диск

Отсутствия разделов недостаточно. Linux может использовать файловую систему
или LVM непосредственно на целом диске.

Мы объединяем сведения из нескольких источников:

- `pvs` — какие устройства уже распознаны как PV;
- `lsblk` — дерево устройств, тип, read-only и точки монтирования;
- аппаратные факты Ansible — разделы, holders, removable и число секторов.

Перед сравнением PV их пути дополнительно разрешаются через
`readlink --canonicalize-existing`. Один диск может иметь имя `/dev/sdb`
и ссылку `/dev/disk/by-id/...`; простого сравнения разных строк недостаточно.
Если путь PV нельзя разрешить, роль останавливается, а не объявляет его свободным.

Кандидат должен пройти все условия в [select_device.yml](tasks/select_device.yml):

| Условие | Зачем |
| --- | --- |
| Допустимое имя `sd*`, `vd*`, `xvd*`, `nvme*n*` | Ограничить поддерживаемые типы имён устройств |
| `type == 'disk'` | Не выбрать раздел или логический том |
| Не read-only | На устройство можно записывать |
| Нет дочерних устройств | Не трогать уже разделённое или используемое дерево |
| Нет mountpoints | Исключить смонтированную файловую систему на целом диске |
| Нет разделов в facts | Дополнительная проверка отсутствия разметки |
| Нет holders | Исключить устройства, используемые вышележащими блочными устройствами |
| Не removable | Не выбрать съёмный носитель |
| Секторов больше нуля | Отбросить пустые или неполные сведения об устройстве |
| Нет в списке PV | Не выбрать PV, даже если он не входит в VG |
| Совпадает с явно указанным устройством, если оно задано | Сузить автоматический выбор |

### Фильтры на примере

```jinja2
item.mountpoints | default([]) | reject('equalto', none) | list | length == 0
```

`lsblk` может вернуть `[null]` для диска без монтирований. `none` в Jinja
соответствует `null` в JSON. Фильтр `reject` убирает эти элементы, после чего
проверяется отсутствие настоящих точек монтирования.

`default` подставляет значение для отсутствующего поля. Это не универсальное
средство скрывать ошибки: важно выбрать безопасное поведение.
В этой роли неизвестный `removable` считается `'1'`, а неизвестный размер —
нулём. Такой диск не пройдёт выбор. Даже если другие отсутствующие списки
заменяются пустыми, отсутствие аппаратных фактов целиком не делает диск
допустимым кандидатом.

В условии:

```jinja2
create_disk_device == '' or item.name == create_disk_device
```

пустой параметр разрешает автоматический выбор. Непустой разрешает только
указанный путь, но все остальные ограничения всё равно должны выполняться.
Здесь ожидается поддерживаемое имя вроде `/dev/sdb`; произвольная ссылка
`/dev/disk/by-id/...` не является поддерживаемым входным значением этого параметра.

После фильтрации требуется ровно один кандидат. При нуле или двух роль
останавливается. Выбор «первого попавшегося» был бы скрытой зависимостью
от порядка устройств, а не осмысленным решением.

У NVMe имя диска заканчивается цифрой, поэтому раздел называется
`/dev/nvme0n1p1`. Для `/dev/sdb` получается `/dev/sdb1`. Эту разницу роль
учитывает отдельно.

## 11. Сигнатуры: проверка до разметки и после неё

`wipefs --no-act --json` читает распознаваемые сигнатуры без их удаления.
Это могут быть признаки файловой системы, RAID, LVM или таблицы разделов.

По умолчанию роль требует, чтобы список сигнатур был пустым.
Параметр `create_disk_wipe_signatures: true` разрешает очистку, но не отменяет
проверки mounted/PV/holders и других признаков занятости.

Уже распознанный существующий PV не станет кандидатом даже с этим флагом.
Например, флаг полезен для остаточной сигнатуры на смещении будущего раздела,
если оператор отдельно подтвердил, что диск предназначен для разметки.

Почему проверка выполняется дважды? Сигнатура может лежать не в начале диска,
а на смещении, которое после создания GPT окажется началом `/dev/sdb1`.
Поэтому сначала проверяется целый диск, затем новый раздел.

Здесь есть важное ограничение: вторая проверка происходит **после** создания
GPT. Если роль остановилась на внутренней сигнатуре, таблица разделов уже
изменена. Ansible не выполняет автоматический откат предыдущих задач.

Также отсутствие сигнатур не доказывает отсутствие любых данных. Сырые
данные без известных меток эта роль не распознаёт. Назначение диска должен
подтвердить оператор.

## 12. Этап изменений: почему важен порядок

[provision.yml](tasks/provision.yml) выполняется после предварительных проверок.

1. Если явно разрешено, удаляются сигнатуры целого диска.
2. `community.general.parted` создаёт GPT и раздел от `1MiB` до конца диска.
3. `partprobe` сообщает ядру об изменении таблицы разделов.
4. `udevadm settle --timeout=30` ждёт обработки очереди событий udev.
5. `wait_for` ждёт появления пути нового раздела.
6. `findmnt` проверяет, что раздел не успел смонтировать другой сервис.
7. Проверяются и, только с разрешением, удаляются сигнатуры нового раздела.
8. После ожидания udev повторно проверяется, что выбранная VG не появилась.
9. Создаются VG и LV, затем XFS, каталог и монтирование.

Создать раздел в таблице и увидеть готовое устройство в ядре — разные события.
Поэтому одного успешного `parted` недостаточно для немедленного вызова LVM.
`wait_for` подтверждает наличие пути, а не доказывает полную готовность
всей цепочки хранения.

### failed_when на примере findmnt

```yaml
register: create_disk_partition_mount
changed_when: false
failed_when: create_disk_partition_mount.rc != 1
```

Обычно Ansible считает код 0 успехом. Для этой проверки ожидается код 1:
монтирование не найдено. Код 0 означает, что оно найдено, и роль должна
остановиться. Другие коды тоже останавливают задачу.

Однако код 1 у `findmnt` может обозначать и ошибку, а не только отсутствие
совпадения. Текущая проверка различает коды, но не доказывает отсутствие
всех возможных ошибок самой утилиты. Это ограничение стоит помнить при
расследовании необычных результатов на конкретной системе.

### Почему повторно читается список VG

Между выбором имени и его использованием другой процесс мог создать группу.
Повторная проверка позволяет обнаружить часть таких изменений.
Она не является блокировкой: остаётся промежуток между проверкой и созданием.
Поэтому запускать эту роль и другие операции provisioning на одном сервере
нужно последовательно.

## 13. Параметры модулей LVM, XFS и mount

```yaml
community.general.lvg:
  vg: '{{ create_disk_selected_vg }}'
  pvs: '{{ create_disk_selected_partition }}'
  remove_extra_pvs: false
  state: present
```

Модуль `lvg` умеет не только создавать VG, но и изменять состав существующей.
Если передать существующее имя и другой список PV, можно затронуть старую
группу. Поэтому сначала выбирается свободное имя и дополнительно явно
отключается удаление лишних PV через `remove_extra_pvs: false`.

Модуль сам подготавливает новый PV при необходимости. Отдельная команда
`pvcreate` в задачах роли для этого не нужна. Безусловные `--force --yes`
из исходного варианта больше не передаются: политика очистки теперь вынесена
в отдельные явные проверки и операции.

```yaml
community.general.lvol:
  vg: '{{ create_disk_selected_vg }}'
  lv: '{{ create_disk_selected_lv }}'
  size: 100%FREE
  shrink: false
  state: present
```

`100%FREE` означает всё свободное место в VG на момент выполнения, а не
«поддерживать этот LV размером во весь диск навсегда». Такой размер не является
общим решением для идемпотентного управления уже существующим LV.
`shrink: false` запрещает уменьшение. В нашей модели VG новая и отдельная,
поэтому это подходящий вариант первоначального выделения места.

`community.general.filesystem` создаёт XFS на пути `/dev/<vg>/<lv>`.
Параметр `force: false` не разрешает принудительно перезаписать обнаруженную
другую файловую систему.

Затем `file` создаёт каталог, а `ansible.posix.mount` с `state: mounted`
обеспечивает монтирование сейчас и запись в `/etc/fstab`. Это отличается
от `state: present`, который управляет записью в fstab без требования
немедленно смонтировать файловую систему.

В конце `set_fact` формирует результат:

```yaml
create_disk_result:
  device: /dev/sdb
  partition: /dev/sdb1
  vg: vg_data
  lv: lv_data
  mount_point: /data
```

Его можно показать следующей задачей playbook:

```yaml
  tasks:
    - name: Показать созданное хранилище
      ansible.builtin.debug:
        var: create_disk_result
```

В примере playbook с секцией `roles` обычные задачи из секции `tasks`
выполняются после ролей. Этот факт — отчёт о выбранном и созданном хранилище,
а не отдельная проверка того, что оно переживёт перезагрузку.

## 14. Идемпотентность и повторный запуск — разные вопросы

Идемпотентность означает, что повторное применение желаемого состояния
не требует новых изменений, когда это состояние уже достигнуто.
Многие Ansible-модули поддерживают такой подход, но из этого не следует,
что вся роль автоматически стала идемпотентной.

Наша роль — одноразовое создание нового хранилища:

| Ситуация | Поведение |
| --- | --- |
| Новый диск, `/data` отсутствует | Создаёт первый том |
| Новый второй диск, `/archive` отсутствует | Создаёт отдельную следующую пару VG/LV |
| Повтор с существующим `/data` | Защитный отказ до разметки |
| Сбой после создания раздела | Повтор не подхватит диск с разделом автоматически |

Чтобы сделать роль сопровождения существующих томов, нужно отдельно
спроектировать, как доказать соответствие «папка → файловая система → LV →
VG → PV → нужный диск», а затем определить разрешённые операции восстановления.
Просто убрать отказ при существующем каталоге недостаточно.

Пример частичного сбоя: GPT и VG созданы, а создание XFS завершилось ошибкой.
Успешные предыдущие задачи останутся выполненными. `block`/`rescue` может
организовать обработку ошибки, но сам по себе не делает операции транзакцией
и не откатывает диск.

Поэтому здесь нет автоматического «очистить всё и повторить»: после сбоя
сначала нужно изучить фактическое состояние и определить безопасный следующий шаг.

## 15. Как проверять такую роль

Разделяй три разных вида проверки.

**Синтаксис.** `ansible-playbook --syntax-check` обнаруживает часть ошибок
структуры и загрузки задач. Он не доказывает правильный выбор диска и не
выполняет реальную разметку.

**Логика на подготовленных данных.** `tests/run.py` запускает настоящие задачи
выбора имён и устройств, подставляя синтетические отчёты вместо чтения дисков.
Есть 6 сценариев выбора имён, 13 сценариев устройств и 1 проверка отказа
полной роли при существующем каталоге — всего 20.

```sh
python3 tests/run.py
```

Запускай команду из корня репозитория с установленным `ansible-playbook` в PATH.
В успешном прогоне ожидается `failed=0`, `changed=0`. Значение `rescued`
может быть ненулевым: некоторые сценарии специально вызывают отказ, затем
перехватывают его и проверяют, что выбор действительно был запрещён.

`rescue` не должен превращать любой сбой в успех. Например, проверка папки
дополнительно проверяет сообщение об ожидаемой причине отказа. Сценарии
устройств проверяют факт отказа, но не все его возможные причины; точность
таких проверок можно улучшать.

**Интеграция.** На одноразовой VM с отдельным пустым диском нужно выполнить
настоящую роль, проверить GPT, PV/VG/LV, XFS, mount и fstab, записать тестовый
файл. Затем добавить второй диск, запустить с другой папкой и проверить
новый том и сохранность первого файла. После перезагрузки нужно проверить
оба монтирования.

Подробный порядок есть в [README](README.md#проверки). В текущей подготовленной
облачной среде интеграционный тест на VM не выполнялся. Прошедшие 20 сценариев
подтверждают проверенную логику выбора и отказов, а не всю работу с реальным
хранилищем.

## 16. Как строить собственные роли по этапам

Начинай с описания результата и ограничений обычным языком, а затем превращай
каждый пункт в задачу или проверку.

1. **Сформулируй контракт.** Что создаём? На каких ОС? Что должен передать
   пользователь? Что делать при повторе и частичном сбое?
2. **Определи интерфейс.** Положи переопределяемые параметры в `defaults`,
   задай безопасные значения по умолчанию и понятные имена с префиксом роли.
3. **Проверь ввод.** Типы, форматы, обязательные параметры, несовместимые режимы.
4. **Собери сведения.** Используй facts, специализированные модули и
   структурированные отчёты JSON. Не выдавай ошибку чтения за пустое состояние.
5. **Отдели решение от применения.** Сначала вычисли выбранные объекты,
   затем проверь однозначность выбора. Эту часть проще тестировать отдельно.
6. **Выстрой зависимости.** Создание раздела должно предшествовать PV,
   файловая система — монтированию; асинхронные события требуют ожидания.
7. **Продумай ошибки.** Где нужен отказ? Какие изменения уже могли произойти
   к этому моменту? Можно ли безопасно продолжить? Если нельзя — сообщи об этом.
8. **Проверь итог.** Выбери функциональную проверку, которая может обнаружить
   неработоспособность, а не только наличие процесса или корректный YAML.
9. **Добавь отрицательные сценарии.** Проверяй не только успешное создание,
   но и запрет неоднозначных или опасных действий.
10. **Документируй границы.** Поддерживаемые платформы, повторные запуски,
    гонки, непроверенные интеграционные сценарии и необходимые права.

Избегай `ignore_errors: true` или `failed_when: false` только ради зелёного
вывода. Такие настройки допустимы, когда ты понимаешь все ожидаемые исходы
и дальше явно разбираешь их, но опасны при чтении состояния хранилища.

Также не стоит сразу обобщать роль на любые типы дисков и ОС. Явный отказ
для неподдерживаемого случая обычно понятнее, чем непроверенная универсальность.

## 17. Упражнения без изменения дисков

Эти задания можно выполнить чтением кода и дополнением тестов выбора:

1. Заняты VG `vg_data`, `vg_data-2`, а также LV `lv_data-1`.
   Какая пара будет выбрана? Ответ: `vg_data-3` и `lv_data-3`.
2. Есть два свободных диска `/dev/sdb` и `/dev/sdc`. Что произойдёт без
   `create_disk_device`? Ответ: отказ из-за неоднозначности.
3. Укажи `/dev/sdc`, но добавь его в список PV в тестовых данных.
   Изменится ли решение? Ответ: диск будет запрещён, несмотря на явный выбор.
4. Найди в тестах случай с `mountpoints: [None]`. Объясни, зачем нужен
   `reject('equalto', none)` и почему нельзя проверять только длину исходного списка.
5. Добавь проверку для диска с `sectors: '0'`. Он не должен стать кандидатом.
6. Измени базовые имена в сценарии выбора на `vg_logs` и `lv_logs`.
   Проверь, что при занятой базовой паре выбираются `vg_logs-1` и `lv_logs-1`.
7. Объясни, почему `changed_when: false` у команды удаления файлов
   не сделает её безопасной. Ответ: это настройка отчёта, а не запрет изменений.

Практику с `parted`, `wipefs` и LVM выполняй отдельно на собственной одноразовой
VM. Для изучения `loop`, `when`, `assert`, `set_fact` и JSON настоящие диски
не требуются.

## 18. Что можно улучшать дальше

Это направления будущей работы, а не уже реализованные возможности:

- Добавить интеграционные тесты на VM, включая второй диск и перезагрузку.
- Явно проверять итоговую цепочку устройств и монтирование после создания.
- Продумать поддержку стабильных путей дисков `/dev/disk/by-id/...` на входе.
- Спроектировать межпроцессную блокировку и повторную проверку занятости
  устройства непосредственно перед изменением. Одного выбора свободного
  имени недостаточно для защиты от всех параллельных операций.
- Улучшить различение ошибок `findmnt` и ожидаемого отсутствия монтирования.
- Сделать отдельный режим сопровождения уже созданных томов, если потребуется
  идемпотентный повтор и восстановление после частичных сбоев.

При любом из этих улучшений сначала опиши ожидаемое поведение и добавь
сценарий, который способен обнаружить нарушение этого поведения. Затем
меняй задачи роли: так будет понятно, для чего появилась каждая новая проверка.
